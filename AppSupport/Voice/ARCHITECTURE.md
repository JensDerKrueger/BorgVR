# BorgVR assistant core

The interactive assistant is an opt-in Swift module shared by macOS, iOS and visionOS. It coordinates requested work against the live application. It has no UI references and does not require a Python agent, WebSocket session, MCP listener or GSC interpreter. It does not observe or learn in the background.

## Authority and decision loop

- `BorgVRAssistantCore` uses three separate model request types. Intake only sees the current user message and separates information, answers and ordered tasks. The state updater only sees the authoritative app snapshot, prior working notes and new evidence. Execution sees the active task, current state and notes, applicable tools and guidance, and any recent results or render evidence needed for the task. Only execution proposes operations; Swift runs them.
- `AssistantWorkspace` is the application interface. `VoiceAgentController` binds start, stop and local consent to that interface. `BorgVRVoiceAgentBridge` uses the in-process MCP router and existing command services, including file pickers and confirmations for consequential changes. Model arguments cannot grant consent.
- The workspace tracks the dataset opening and manual revisions. The assistant waits for ongoing user operations, batches their completed change domains, and updates the notes from the latest snapshot and changed fields. Stale decisions and note updates are discarded. A stopped task cannot start another command, and an uncertain mutation is never automatically replayed. Cancellation does not undo completed operations.
- A successful command receipt is not proof that the visual goal was met. The UI reports confirmed changes separately from the model's text. A clarification carries the specific question and answer into the current task. The optional encrypted conversation archive contains text, confirmed tool receipts and working notes, not image evidence. Previous chat messages are not included in ordinary model decisions. Provider changes invalidate the local conversation owner.
- `VoiceAgentModelClient` uses structured HTTP requests. vLLM uses `/v1/models` and `/v1/chat/completions`; OpenAI uses `/v1/responses` with `store: false`. OpenAI uses system TLS and a separate Keychain key and image consent. Microphone audio, passthrough and camera images are not provided to either model. The application's local speech recognition setting remains independent of the model provider.
- Execution starts with the assistant-visible operation catalog in the system prefix. A selected method keeps full schemas for its tools and offers only names and short descriptions for unrelated tools; local validation still uses every available tool's full schema and adds it to the next request after an argument error. Definitions and keys have a deterministic order. No catalog or images are sent to intake or the state updater.
- Successful reads are working evidence, separate from change receipts. The core marks them with `observation_returned` and carries structured results within the event budget; oversized evidence is explicitly marked truncated. A reply correction applies to the current decision, not to later steps after progress. The model can answer once the evidence suffices or continue when it still needs a specific observation or change. Provider output constraints distinguish decisions from tool names, and restrict the latter to the catalog; local checks still enforce argument schemas and current availability.
- One saved profile is selected at a time. Each profile has its own Keychain credential and render consent. For vLLM, credentials and certificate trust are tied to the saved HTTPS origin. On demand, the modal editor intersects OpenAI's `/v1/models` for the draft's key with the documented model IDs for image input and Structured Outputs on the Responses API. Listing does not invoke any model. Testing an OpenAI draft uses a synthetic image and the same strict schema as normal operation. Neither action sends workspace data or saves the draft; only **OK** commits it. Switching the active profile stops the previous task and clears its conversation context.

## Knowledge packages

The example is [`assistant-knowledge.json`](assistant-knowledge.json). An edited JSON file can be imported in **Settings > AI Assistant > Assistant options > Import knowledge package**. It replaces the bundled package for the next task, is validated before use, and can be reset without a rebuild. An in-progress task uses its original package.

The `rules` section contains unique IDs, an `operations` list of language-neutral tool names (empty for general rules), and `text`. The graph root and leaves can reference rules with `ruleIDs`. Only root rules and unlinked general rules are sent in the system prefix for execution. The operation determines which leaf rules to supply; the selected method disambiguates shared operations, but a tool outside that method can still get its own rules. If a mutation's rules were not present in the current decision, BorgVR supplies them and asks the model to decide again before executing. An observation returns its rules and those of the next apply leaf with the evidence; a confirmed change can return the verify rules. Unlinked operation rules still work in older packages. The old `topics` field is ignored. The 12 KiB rule-text budget applies to any one decision, rather than the whole package. Selecting or importing a rule never grants permission.

`workflows` are data: a unique `inspect.*` ID, a description and a short list of typed investigation steps. Supported primitives are `screenshot` (a bounded width) and `intensityScan` (difference threshold, palette and an optional Smoothstep `transitionWidth`). Older imported definitions without `transitionWidth` retain the isolated-band behavior configured by their initial intervals, preview limit and minimum interval width. New compositions and options need no app rebuild; new primitives need Swift. No arbitrary source code, paths, network access, or loops from packages are executed.

The current dataset's short catalog description and dimensions are part of the decision state, even before a tool call. They do not establish which structures are present. The text-only reply review receives observation availability and whether rendered images were shown, not the images themselves. It distinguishes unsupported content claims from announcements of unexecuted work. For one corrective decision, the latter requires a tool decision or a real clarification instead of a second finish draft. An unsupported content claim uses the same constraint only while an unused visual observation is available. Neither constraint bypasses authorization, local argument validation, or verification.

A validated tool decision can carry an optional short, plain-text next step for the user. The controller displays it while the request runs and discards it at completion or cancellation. It is neither a confirmed result nor part of the conversation history. Rejected drafts and invalid actions do not publish progress text.

The local response-length preference (concise, normal, or detailed) is included in the decision and final-reply context. It changes wording, not the number of updates, available tools, or connection identity. A running request keeps the preference it started with.

The core keeps the ordered plan from intake locally. Execution receives only the active request, plus actual outcomes from completed tasks, not upcoming tasks or the original combined prompt. It returns `advance` to complete an intermediate outcome or mark it blocked; a blocked task stops the remainder. An information-only message updates the state without entering execution. Notes are updated at the start and on meaningful new evidence or app changes, not for frames or screenshot IDs alone. No fixed rule determines when a particular note expires.

The optional `decisionGraph` is a version-1 package field with stable node IDs and typed links: `root` → `goal` → `method` → `observe`, `apply`, or `verify`. Steps can be shared by several methods. Loaded-volume tasks start at the root. The model can optionally name a suggested method alongside its next decision and quote an explicit user directive. The graph records this as guidance, not as an execution constraint. An absent or unknown route cannot block an otherwise valid action. The model should follow the user's actual constraints, but can choose any available operation that serves the request, including one outside the graph. Existing local permissions and command validation are unchanged. Debug builds log the route IDs and origin, not the quotation.

The bundled visibility goal offers transformation, clipping, transfer-function adjustment, render mode/lighting, and editing. For an uncertain named view the transform branch can show the XYZ-colored dataset bounds and zoom out temporarily if the box is cropped. The built-in `inspect.orientation` workflow captures the same pose with and without lighting through the normal screenshot command, or one image in isovalue mode. It restores the original mode before sending the labeled images together and does not edit the transfer function. Each image gets a separate model finding. BorgVR accepts one clear match and does not dispatch a further rotation for that goal, including after restoring temporary framing aids. External changes invalidate the observation; a partial comparison is never sent. The colors describe the local data axes, not anatomical direction. Transfer-function leaves link rules for interpreting a sweep, reading an existing curve, editing, and checking the live result. The model still has to interpret the request and evidence; the graph does not establish that a visual hypothesis is correct.

The default sweep slides the same Smoothstep through all four RGBA components of one scalar channel. The ramp spans 6 percentage points. It moves from 0% to 100% in 1% steps without jumping back, including the transparent endpoint (101 renders). It reads the original TF, then uses the usual commands to set each curve, wait for a new frame, and take a screenshot. Each step changes the editable presentation and participates in regular persistence and recording. The sweep restores the exact original curve on completion, or on a capture error if the state was not changed by the user. On Stop, it leaves the current curve in place. The normal screenshot path (also used by GSC and MCP) waits for a volume frame with no brick requests and retries if the capture frame requests more bricks. Consecutive images are compared on the fly. Adjacent significant changes form one transition; the log records each range and its strongest step. Up to four transitions, ranked by their peak change, contribute a candidate four steps after their end, capped at the next transition or end of the sweep. A change does not identify a material. Applying an inspected preview is a separate action that replaces that channel's opacity and palette.

The last completed sweep of a single-channel screen dataset is kept in memory once the original TF is restored. A subsequent sweep request for the same dataset opening, channel, and scan configuration can reuse its candidates when the orientation differs by less than 5 degrees and translation differs by less than 0.02 normalized scene units. The other render state, viewport aspect, edit state and voxel-edit revision must still match. A hit attaches the older candidates as sweep evidence and does not change the live TF. The cache is not used for immersive viewpoints or multichannel volumes.

Applying a sweep preview takes a fresh screenshot through the ordinary capture command. The live image, not the older candidate images, is the check of the applied result. Previously seen candidates can be applied again, and repeating a read or sending identical relative commands does not force a final reply. A finish disguised as a tool can still use the existing tool-free reply fallback in a task without subgoals.

Executed attempts carry `attempt_id` and an execution outcome. A changed transform records the before and after values. The next ordinary model decision may also return an `assessment` of an actual attempt, with a short finding and the outcome helpful, not helpful, or inconclusive. The bounded `trial_findings` list retains these model assessments independently of execution receipts and does not block repeats. A missing assessment means the result has not been assessed. Recoverable read and structured-decision errors go back to the model for bounded correction. Connection failures and uncertain mutation effects are not retried as prompt corrections.

A decision with a live render also returns a `goal_check` for the active request, separate from an operation receipt or trial assessment. A visible mismatch can accompany the next corrective command in the same response. If the model tries to close an unresolved goal without a reason it cannot proceed, BorgVR returns the finding to the execution loop once for that image. A genuine blocker is reported as an incomplete result, not a tool error or a completed subgoal. A new render is evaluated independently, and external changes invalidate the old live check. Debug builds show the structured finding on an `Assistant goal check:` line.

## Verification and scope

Debug builds show generated text or decision JSON (including partial output) on `Assistant model output:` lines, and dump the live snapshot and working notes on `Assistant app state:` and `Assistant conversation state:` lines in the Xcode console. Release builds do not emit these lines. These may include user information or dataset metadata. They do not dump raw images, credentials, or reasoning fields.

The unified log also records the start and duration of model calls, payload sizes, image count and transport error codes without recording any request or response content. The model-facing transfer function preview is capped at 192 uniformly spaced RGBA rows so it fits as structured evidence in the next decision. The native tool result and the renderer retain full resolution.

`sh Scripts/test-voice-agent.sh` covers schema validation, the native sweep loop with synthetic images and decisions, stale evidence, stop, and both provider payloads and replies. Pass the `macOSApp` Debug products directory for real BorgVR bridge/GSC/security tests. On a running GPU host `sudo ./setup.sh test` checks HTTPS, key enforcement, endpoint restrictions, vision and structured output using a synthetic image. Local tests do not establish how well a specific model recognizes anatomy or other structures.

Point 2 (target-directed visualization) is the first focus. Direct commands share the execution path. Learned personal routines and an exploratory collaborator are future work, not hidden modes in the current application.
